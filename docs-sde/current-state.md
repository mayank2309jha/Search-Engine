## Phase 12 (same day) — Dockerized, with a real memory-safety incident and fix

Full detail (every error message, every dead end): `query-server/benchmarks-phase11-12.md` and `runningUpdates.md`'s Phase 12 section. Summary: `query-server/Dockerfile` + repo-root `docker-compose.yml` now exist. Hit and fixed, in order: a build-time CUDA-torch download that filled Docker Desktop's VM disk to 16GB and corrupted its filesystem (recovered by deleting and recreating the VM disk); a broken NLTK downloader in this build context (bypassed with plain stdlib); a SQLite WAL-mode read failure against the mounted `crawler.db` (real fix in `app/crawler_db.py`: `immutable=1` on the connection URI); a HuggingFace model cache invisible to the non-root container user (fixed with an explicit `HF_HOME`). Memory was calibrated live against real measurements, not guessed: a 2GB limit nearly OOM-killed the container within 30 seconds; the final, verified value is **5GB**, which settles at **4.27GB (85%) under real query load — ~730MB of genuine headroom**. A `docker-build` CI job (build, boot, health check, authenticated search, 401-without-key check) was added to `.github/workflows/ci.yml`, validated but not yet run on real GitHub infrastructure.

- ~~The in-memory LRU cache and rate limiter are per-process~~ — **Redis-capable since Phase 9, still in-memory by default.** `REDIS_URL`-driven, graceful fallback if unset or unreachable. Still never exercised against a real Redis instance — tested against a fake client only.
- **`title` isn't indexed on the C++ side, yet.** Fix exists (Phase 8), verified functionally, **still not merged** — teammate-owned code (`src/index.cpp`) pending review. Now more clearly worth landing: it would improve ranking over all 19,514 real documents, not a synthetic test DB.
- **PageRank's signal is real now, but flat.** Resolved the old "sums to ~0.008" bug (see above) — it now correctly sums to 1.0 across 34,176 discovered URLs. But the *distribution* is nearly uniform: min 2.91e-5, avg 2.93e-5, max 8.78e-5 — the highest-scored page is only ~3x the average, not the multiple-orders-of-magnitude spread PageRank usually produces on a real, hub-heavy web graph. Worth a closer look before leaning on this signal — possibly the dampening factor, possibly the crawl's link structure being unusually flat (many pages linking to few others, few pages being heavily linked back).
- **The crawl picked up real, disclosed noise.** Sampling `crawler.db`'s titles directly surfaced a Google account sign-in page, several parked-domain listings (`hugedomains.com`), and an affiliate-marketing domain (`clickbank.net`) among the 19,514 pages — alongside genuinely good content (`docs.python.org`, `bbc.com`, MDN). One page (an EBSCO subject-list page) is 1.7MB of content, a 170x outlier over the ~9.7KB average. None of this breaks anything, but it's a real crawl-quality question worth a look before the next, much bigger crawl.
- **Startup and test-suite cost jumped with real data — measured, not estimated.** `data/index.bin` alone now takes ~28s to parse in pure Python (was near-instant at 240 docs); full server startup (index load + spellcheck-dictionary build over 854,906 terms + embedding rebuild for 19,514 docs) takes ~3 minutes; the full `pytest` suite went from ~13s to **~2m35s**, almost entirely from fixture costs paying that same startup tax. None of this is broken — it's the in-memory-everything architecture meeting real data for the first time, exactly where `cpp_index_reader.py`'s "loads the whole index into memory in one pass" caveat said it eventually would.
- **Semantic search latency is now measurable, and it's not fast.** A `rerank=true` query against the real corpus took **~3.0 seconds** (vs. ~190ms for a lexical-only query) — the whole-corpus embedding-similarity augmentation step is O(19,514) per query with no ANN index. Fine for a demo today; a real, disclosed ceiling well before 2M pages.
