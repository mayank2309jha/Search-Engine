Run each query against `http://127.0.0.1:8000/search?q=...` and record what
actually came back. Corpus: **1000 documents across 10 domains** (tech,
healthcare, finance, education, sports, entertainment, food, travel,
science/environment, law/government) in `data/corpus.json`. Generated by
`scripts/generate_corpus.py` — see that file for the exact entity/topic
vocabulary each domain draws from, which is what several "Expected Result"
columns below rely on.

## 9. Phase 5 — semantic re-ranking (`rerank=true`)

These are deliberately **paraphrase queries**: they share few or no literal
(stemmed) words with the target documents' actual text. Verified behavior,
not a prediction — running these live surfaced two real, fixed issues worth
knowing about before reading the rows below:

- A pure paraphrase query often trips the corpus-derived spellchecker (e.g.
  "fighting" and "warming" don't literally appear anywhere in this generated
  corpus, so they're flagged `unknown_words`). With `rerank=false` this
  correctly returns `"No results found."` — spellcheck/BM25 have no way to
  match a word that isn't in the corpus at all. With `rerank=true`, that
  early rejection is bypassed specifically so semantic matching gets a chance
  (see `app/main.py`'s `unknown_words and not rerank` check).
- Semantic re-ranking only *augments* (surfaces documents BM25 missed
  entirely, via whole-corpus embedding similarity) when the query has no
  explicit hard constraint (no `AND`/`NOT`/phrase) — a confident boolean query
  is never diluted with semantic-only extras that might not actually satisfy
  it. See `app/semantic.py`'s `semantic_rerank` docstring.

## Notes / Known Limitations

- Phrase adjacency is computed on the stemmed, stopword-stripped token stream — a
  phrase like "climate research" will match even across an intervening stopword
  in the original text, since stopwords are removed before positions are assigned.
- The `location` field is not part of the indexed text, so location-only queries
  return nothing relevant.
- Query #19/#21 (`development`/`developments`) are intentionally cross-domain —
  useful for eyeballing whether ranking looks sane when a term isn't
  domain-specific, not just when it obviously is.
- Rows 51-55 depend on `rerank` being wired into `/search` (Phase 5). If that
  parameter doesn't exist yet, skip section 9.
